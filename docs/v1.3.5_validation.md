# v1.3.5 상세 검증 기록

## 검증 원칙

화면 자동화는 사용 중인 데스크톱이 아닌 독립 Xvfb 가상 화면에서 BlastEm을
실행했다. 각 장은 시나리오 셀렉트로 새로 진입했으며, 완료 검사용 ROM은
이름·클래스·이벤트 코드를 유지한 채 전투 시간을 줄이는 진단 필드만 바꿨다.
따라서 한 세이브로 1장부터 31장까지 연속 플레이한 기록은 아니고, 각 장의
진입·전투·결과·저장·분기 표면을 독립적으로 재현한 전 장 회귀 검사다.

## 지휘관·배치 정적 검사

- 일본판 원본의 시나리오 1~31 고정 레코드 340개를 모두 열어 레코드 수와
  범위를 확인했다.
- Original과 Normal은 시나리오 31 데몬로드 ID 수정 한 바이트 외에 이름,
  클래스, 레벨, AT/DF, 용병, 진영, 숨김 상태, 좌표가 원본과 같다.
- Hard는 승인된 Standard Hard 대상의 AT/DF·용병·태그 차이와 공통 데몬로드
  ID 수정 외의 시나리오 레코드 차이가 없음을 검사했다.
- Hard의 300개 대상 적 레코드와 런타임 보정 루틴은 기존 승인 계획으로 다시
  검증했다.

## 진입과 첫 턴

| 판본 | 검증 장 | 결과 |
| --- | ---: | --- |
| Original | 1~31 | 31/31 통과 |
| Normal | 1~31 | 31/31 통과 |
| Hard | 1~31 | 31/31 통과 |

시나리오 식별은 준비 화면만 보고 추정하지 않고, 로드된 런타임 고정 지휘관을
해당 장의 원본 레코드와 대조했다. 이어서 실제 출격과 첫 턴 명령 화면 또는
원작에서 허용된 첫 턴 패배 경로까지 진행했다.

## 전투 결과·저장·엔딩

- Normal과 Hard의 1~31장을 각각 새 후보 ROM에서 실행했다.
- 마지막 대상은 실제 공격 또는 해당 장의 실제 런타임 승리 조건으로
  쓰러뜨렸고, 가능한 장은 대상 HP 0과 격파 플래그를 GST에서 확인했다.
- 결과 화면 뒤 저장 메뉴가 있는 장은 저장 메뉴까지 진행했다.
- 13장은 조름 격파 뒤 발가스 증원과 제시카의 실제 매직애로 사용을 확인했다.
- 18장은 대룡(이름 ID `0x54`, 클래스 `0x5E`), 20장은 피아스(이름 ID
  `0x73`, 클래스 `0x5D`)를 확인한 뒤에만 HP를 1로 만드는 보호 래퍼를
  사용했다. 두 대상 모두 Normal/Hard에서 공격 전 HP 1, 공격 후 HP 0과
  격파 플래그 `0x80`을 기록했다.
- 27장은 베른하르트를 실제 공격으로 격파한 뒤 모든 에필로그와 크레딧,
  `Fin`까지 진행했다.
- 31장은 중복 ID를 수정한 데몬로드의 전용 사망 대사와 최종 결과 경로를
  각각 확인했다.

## 키스·레스터·제시카와 룬스톤

- v1.3.1은 키스·레스터의 파이터 룬스톤 첫 행이 정상이고,
  v1.3.2~v1.3.4는 합류 전용 행이 그 자리를 덮어 잘못된 후보가 나온다는
  회귀 경계를 BPS별로 재현했다.
- v1.3.5에서는 키스·레스터의 원본 파이터 행을 유지하고 긴 합류 전용 체인과
  스프라이트 표를 확장 영역으로 옮겼다.
- 키스 파이터 `로드 / 호크나이트 / 힐러`, 레스터 파이터
  `나이트 / 크로코나이트 / 샤먼`, 제시카 워록
  `힐러 / 소서러 / 로드` 세 후보를 가상 화면에서 확인했다.
- Hard 키스는 룬스톤을 실제 장비·사용해 `클래스체인지 가능` 상태와 선택
  화면까지 진행했다.
- 새 게임의 1차 클래스 레벨 10 합류와 v1.3.4의 파이터 레벨 11 이상 구
  세이브 자동 복구 코드는 그대로 유지된다.

## 과거 보고 항목

- 시나리오 6 우물의 룬스톤은 Original과 Hard에서 실제 이동해 획득했다.
- 시나리오 31 데몬로드의 화면 이름·클래스·밸런스는 유지하면서 이벤트가
  요구하는 ID `0x66`으로 연결했다.
- 최종 v1.3.5 ROM과 전체 플레이 후보 ROM의 차이는 판본별 버전 문자열과
  그에 따른 메가드라이브 체크섬 3~5바이트뿐이다. 검증한 게임 코드와
  시나리오 데이터는 최종 배포물과 같다.

## 배포물 검사

- 일본판 2MiB 원본에서 Original·Normal·Hard BPS를 적용한 뒤 세 결과의
  크기 4MiB와 SHA-256을 검증했다.
- BPS 생성 후 역적용 결과가 빌드 ROM과 바이트 단위로 같은지 확인했다.
- Linux x86_64 단일 실행 패처를 로컬에서 만들고 실제 일본판 ROM을 입력해
  세 결과 해시가 매니페스트와 같음을 확인했다.
- Windows, Linux x86_64/ARM64, macOS Apple Silicon/Intel 빌드는 각 네이티브
  GitHub Actions 러너에서 생성·실행·아키텍처 검사하도록 구성했다.
- 실행 패처에는 현재 1.3.5 BPS 세 개와 매니페스트만 넣어 과거 BPS 전체를
  중복 포함하지 않는다.

## 최종 ROM 기준 진단 도구 재검증

- 공통 진단 입력 `roms/builds/Langrisser II (Korean).md`를 최종 Normal
  v1.3.5와 같은 SHA-256
  `724304a728ad9b3202b8d69b4c2afff284291c02e3bc419891e22e5e7f535abd`로
  다시 생성했다.
- 시나리오 11~20·31의 진단 ROM 체크섬 잠금을 최종 버전 문자열·메가드라이브
  체크섬과 시나리오 31 ID `0x66` 기준으로 승격했다. 분기 진단은 일본판의
  오류 ID `0x65`로 되돌리지 않고 v1.3.5 제작 데이터가 그대로 보존되는지를
  검사한다.
- 시나리오별 진단 ROM 테스트 507개가 모두 최종 입력으로 통과했다. 클래스
  전직·마법·상태창·소환 진단과 v1.3.5 변경 테스트를 합친 릴리스 범위는
  593개를 실행해 586개 통과, 7개는 정리한 구버전 ignored 캡처만 요구하는
  기존 증거 테스트라 명시적으로 건너뛰었다.
- 저장소 전체 1,720개도 별도로 감사했다. 결과는 1,559개 통과, 61개 실패,
  89개 오류, 11개 건너뜀이다. 남은 항목은 삭제된 과거 후보 ROM·GST·PNG,
  v1.0~v1.2 보관 릴리스, 현재 제작 ROM과 연결하면 안 되는 구 런타임 해시,
  정리 전 디자인·인벤토리 보고서를 직접 요구하는 레거시 테스트다. 이를
  v1.3.5 통과로 숨기거나 기대값만 바꾸지 않았고, 현재 릴리스 범위 593개와
  신규 전 장 Xvfb 검증을 별도 승인 기준으로 사용했다.
