# 게임 데이터 편집기 구조

`editor/server.py`는 한국어 최신 빌드나 일본어 원본을 읽고, 검증된 ROM
필드만 수정한 별도 ROM을 만듭니다. 출력은
`roms/builds/Langrisser II (Korean Editor Edit).md`이며 기준 ROM을
덮어쓰지 않습니다.

## 시나리오 배치

- 포인터 표: `0x18005E`
- 각 시나리오 헤더 `+0x0C`: 고정 배치 목록 포인터
- 레코드 크기: 36바이트
- 편집 필드: LV `+0x0E`, AT/DF `+0x12/+0x13`, 클래스 `+0x1B`,
  용병 6칸 `+0x1E..+0x23`
- 읽기 전용: 이름 ID, 좌표, 진영, 이벤트 플래그

좌표와 진영은 이벤트가 실행 중에 다시 쓸 수 있으므로 아직 편집하지
않습니다. 클래스 ID만 바꿔도 런타임 마법·소환 권한이 자동으로 붙지는
않습니다.

## 아이템

- 효과 표: `0x060530`
- 아이템당 8바이트: `(효과 종류, 값)` 4쌍
- 가격 표: `0x0A1D32`
- 가격 단위: ROM 값 1당 게임 표시 10P

일반 효과 종류는 AT, DF, MV, 지휘범위, A/D보정, 마법 사거리·대미지,
마법저항, 소환 ID입니다. 경험치 2배, 공격 사거리, 룬스톤 클래스 초기화,
MP 2배 같은 일부 아이템 동작은 개별 코드에 하드코딩되어 있어 현재
편집기에서는 읽기 전용 참고 정보로만 표시합니다.

아이콘은 `captures/run/97e0_item_id01.png`부터 `id37.png`까지의 검증된
320x240 상점 캡처에서 선택 행의 16x16 영역을 잘라 생성합니다.
선택 행은 X=24, `Y=42+16*((ID-1)%5)`입니다.
`tools/build_item_icon_assets.py`가 같은 좌표 계산과 37개 완전성을
검증합니다. 이전 14픽셀 계산은 아래쪽 아이템일수록 다음 아이콘과 섞이므로
사용하지 않습니다. 이 PNG는 에디터 표시 자산이며 ROM 그래픽을 수정하지
않습니다.

## 클래스 체인지

- 지휘관별 포인터 표: `0x08253A`
- 지휘관: 엘윈부터 제시카까지 10명
- 지휘관당 전이: 일반 9개와 최종 1개
- 일반 전이: 현재 클래스 1개와 후보 3개
- 최종 전이: 현재 클래스 1개와 후보 1개, 뒤에 `FFFF`

ROM의 10개 전이 레코드는 10단계가 아니다. 화면은 다음 소유 관계를
실제 최대 5단계 트리로 펼칩니다.

1. 레코드 0: 1단계 시작 클래스에서 2단계 후보 3개
2. 레코드 1..3: 각 2단계 클래스에서 3단계 후보
3. 레코드 4..8: 각 3단계 클래스에서 4단계 후보
4. 레코드 9: 지정된 4단계 클래스에서 숨은 5단계 후보

현재 클래스가 한 지휘관 경로 안에서 중복되거나 클래스 ID 범위를 벗어나면
빌드를 거부합니다.

### 전직 용병 해금

- 클래스 레코드 표: `0x05EDDC`
- 레코드 크기: `0x1C`
- 새 용병 비트 인덱스: `+0x1A`, `+0x1B`
- `FF`: 해금 없음
- 저장값 `00..0F`: 실제 용병 클래스 ID `62..71`

`0x014C68..0x014CAC`의 전직 적용 코드는 두 비트를 지휘관의 기존 고용
비트마스크에 추가합니다. 따라서 에디터의 두 칸은 그 클래스가 전직 시
**새로** 해금하는 용병이며, 전체 고용 목록을 덮어쓰지 않습니다.

### 클래스와 용병 그림

- 일반 클래스 스프라이트 ID 표: `0x05DDE6`, 157개 워드
- 지휘관별 스프라이트 포인터 표: `0x05DB80`, 10개 포인터
- 16x16 스프라이트 그래픽 시작: `0x052980`
- 스프라이트당 128바이트, 8x8 타일 4개

`tools/build_class_sprite_assets.py`는 일본판 ROM에서 일반 클래스 157종의
4개 원본 팔레트와 10명 지휘관의 클래스별 전용 그림을 추출합니다.
시나리오와 클래스 트리는 지휘관 전용 그림을 우선합니다. 지휘관 문맥이
없는 클래스 선택기는 일반 그림을 쓰되, 일반 스프라이트 표가 아니키
대체 그림 `0x18`을 가리키는 플레이어 클래스라면 ROM의 첫 지휘관
오버라이드를 대표 그림으로 사용합니다. 용병 선택기는 항상 일반 클래스
그림을 사용합니다. 클래스 체인지 화면의 다른 CRAM 행은 진영 팔레트가
아니므로 시나리오 진영과 무관하게 검증된 `p1`만 사용합니다. 이전
`class-previews`는 후보 화면의 용병 편성 영역을 자른 것이어서 캐릭터
클래스 그림으로 사용하지 않습니다. 외부 클래스 체인지 표와 이미지
모음은 이름·트리의 육안 대조에만 사용하고 ID 소유권은 ROM을 기준으로
결정합니다.

클래스 이름과 그림이 같아도 ID를 합치면 안 됩니다. 예를 들어 `2D`와
`2E`는 모두 일본 원본에서 파이터로 표시되고 일반 스프라이트 ID도 같지만,
28바이트 클래스 레코드는 `+0x0F`, `+0x10`, `+0x13`이 다릅니다.
고정 배치 전수 조사에서 `2D`는 시나리오 1·2·3·6의 일반 제국 지휘관
12명, `2E`는 시나리오 1의 발드 한 명만 사용합니다. 시나리오 LV/AT/DF는
클래스 레코드가 아니라 각 36바이트 배치 레코드에 별도로 저장됩니다.
나머지 클래스 레코드 필드는 의미와 적용 코드를 검증하기 전까지 편집기에
노출하지 않습니다. 에디터에서는 두 파이터를 육안으로 구분하기 위해
`2E` 대표 PNG에만 보라색 갑옷·빨간 방패 내부 팔레트를 적용합니다.
게임 빌드도 같은 구분을 반영합니다. 원본 `0x7E`의 두 애니메이션
프레임을 확장 ROM `0x2F0000`, `0x2F5900`에 복제해 색 인덱스만 바꾸고,
`2E` 표 항목만 전용 스프라이트 ID `0x53AD`로 연결합니다. 로더
`0x0110F4..0x011104`와 `0x011474..0x01148A`는 16비트 ID를
`ID << 7`로 계산하므로 이 확장 주소를 그대로 읽습니다. `2D`와 원본
스프라이트 `0x7E`는 수정하지 않습니다.

## 통합 빌드

`POST /api/build`는 한 번의 요청에서 다음 데이터를 순서대로 적용합니다.

1. 불러온 모든 시나리오 수정
2. 37개 아이템 가격과 효과
3. 10명 지휘관의 클래스 체인지 경로
4. 157개 클래스의 전직 용병 해금 두 칸
5. MD 헤더 체크섬 재계산

편집하지 않은 전체 데이터를 다시 전달한 회귀 검증에서는 결과 ROM이 기준
한국어 ROM과 바이트 단위로 동일했습니다. 현재 기준 체크섬은 `5ED9`,
SHA-256은
`ba9d3ae0f481a3f1421a1286d5e215fe4d49143d49fc1e32737c9868b66d4d27`
입니다.

## 실험 클래스 디자인 탭

`테스트 체인지`와 `AI 클래스`는 에디터 표시용 PNG만 읽는 비교 화면이다.
두 탭의 매니페스트에는 `rom_effect: none; preview PNG assets only`가
기록되어 있으며 `POST /api/build` 요청에도 이 데이터가 들어가지 않는다.
실제 게임에 적용된 별도 디자인은 시나리오 1 발드의 클래스 `2E`와
시나리오 1·2 로렌의 하이로드 `9B`다. `0B`와 `9B`는 둘 다 원본 이름이
`하이로드`이고 일반 스프라이트 `0x1C`를 공유하지만 별도 28바이트 클래스
레코드다. `0B`는 플레이어 전직용으로 용병 `6A`, `63`을 해금하고, `9B`는
로렌 전용 NPC 레코드라 새 용병 해금이 없다. 로렌 `9B`만 확장 스프라이트
`0x53AE`로 연결해 원본 좌표는 유지하고 청색 계열 인덱스 `4/E/F`를
초록·진초록·금색 `8/9/A`로 바꾼다. `0B`와 다른 NPC 스프라이트는
수정하지 않는다.

두 실험 생성기는 지휘관별 클래스 그림 ID를 묶고 `(단계, 클래스 ID)`로
정렬한다. 같은 그림을 공유하는 묶음의 `group_rank == 0`은 ROM에서
추출한 16×16 PNG와 바이트 단위로 같아야 한다. 그 뒤 순위의 클래스만
변형하며 현재 전체 170개 항목 중 102개가 이 조건에 해당한다.

`tools/build_test_class_sprite_assets.py`는 원본의 검은 윤곽선과
피부·머리카락 주변 얼굴 마스크를 마지막 단계에 복원한다. 밝은색과
어두운색 두 덩어리로 모든 픽셀을 치환했던 첫 실험은 얼굴과 갑옷 경계를
뭉갰으므로 폐기했다.

`tools/build_ai_class_sprite_assets.py`는
`docs/assets/ai-class-source/references/01-original.png`부터
`10-original.png`까지의 실제 ROM 5프레임을 얼굴·머리 정체성
레퍼런스로 사용한다. 이전
`identity-locked-class-boards`는 얼굴 크기와 머리 길이가 원작과 다른
경우가 있어 최종 입력에서 제외했다. 새 원화는 지휘관별
`docs/assets/ai-class-source/character-ai-v3/<character>` 폴더에
보존한다.

각 새 시트는 5×3, 5×2, 4×2, 3×3의 고정 격자와 클래스 ID 순서를
코드에 기록한다. 순수 검은 배경에서 머리·몸과 한두 논리 픽셀 떨어진
지팡이, 검, 날개, 탈것까지 넓은 연결 마스크로 묶어 잘못된 장비 조각만
선택하는 일을 막는다.

이전 변환기는 전경 경계를 자른 뒤 가로와 세로를 각각 16픽셀에 맞춰
늘렸기 때문에 긴 창·날개·말이 있는 원화가 찌그러지고 논리 픽셀 격자가
어긋났다. 이후 15×15 안에 맞춘 결과도 한 줄을 불필요하게 잃었다.
현재 변환기는 종횡비를 유지하며 긴 축에 16픽셀 전체를 쓰고, 가로 중앙과
16번째 행의 바닥선에 정렬한다. 축소는 최근접 표본을 쓰고 희소색 보존에
유리한 최대 범위 15색 팔레트로 정리하므로 투명색을 포함해 최대 16색이다.
생성 프롬프트 단계부터 원본의 머리 길이, 앞머리 방향, 얼굴 크기, 눈
위치를 반복해 요구한다. 쉐리는 `04-original.png`에 맞춘 짧은 단발,
아론과 레스터는 원작처럼 몸 대비 큰 얼굴을 사용한다. 생성 단계의 유사성에
더해 최종 16×16에서는 ROM 얼굴·머리 마스크를 같은 좌표에 덮으므로 눈과
흰자까지 정확히 보존된다. 결과는 `editor/static/ai-class-sprites`에
보존한다.

아론의 상위 클래스는 기본 복장의 흰색·황토색 망토를 정체성 색으로
이어 간다. 로드는 망토를 황토색, 큰 방패를 파랑·하늘색으로 분리하고,
메이지와 아크메이지는 연결된 망토·로브만 흰색·황토색으로 바꿔 분리된
파란 마력 효과와 구분한다. 아크메이지는 흰색을 넓은 주면으로 사용하고
황토색은 주름과 테두리에 남긴다.

엘윈 로드의 오른쪽 방패는 현재 하이로드의 둥근 5픽셀 폭 실루엣과
파랑·금색 격자 명암, 황금빛 외곽을 같은 방식으로 사용한다.

엘윈과 헤인은 같은 ROM 지휘관 그림을 여러 클래스가 공유하는 묶음에서
최저 클래스만 원본으로 남기고, 그 그림을 다시 쓰던 상위 클래스만
디자인한다. 엘윈은 상위 중복 10개를 변경하고 파이터·나이트·샤먼·
매직나이트·세인트·그랑나이트·킹 7개는 원본을 유지한다. 헤인은 상위
중복 11개를 변경하고 워록·로드·매직나이트·프리스트·비숍·세인트 6개는
원본을 유지한다.

엘윈의 주력 보병 계열은 사용자가 선택한
`docs/assets/direct_16x16_01_elwin.png` 5단계 합본을 사용한다.
1단계 파이터는 참고만 하고 ROM 원본을 유지하며, 2~5단계를 각각 로드,
하이로드, 소드마스터, 히어로에 연결한다. 하이랜더·비숍·메이지·
아크메이지·나이트마스터·실버나이트는 클래스 성격이 다르므로 별도
원화를 사용한다. 메이지와 아크메이지는
`character-ai-v3/elwin/elwin-mage-archmage-source-v3.png`의 보병
마법사 2단계 시트로 교체했다.

리아나부터 제시카까지 9명은 모두 `character-ai-v3`의 캐릭터별 전용
시트를 사용한다. OpenAI 이미지 생성 프롬프트에는 메가드라이브 논리
16×16 격자, `references/XX-original.png`의 머리 실루엣·얼굴 크기·
방향·눈 위치 유지, 클래스별 갑옷·로브·망토·방패·무기·탈것만 변경하는
조건을 반복한다. 이전 AI 보드는 새 생성의 얼굴 레퍼런스로 사용하지
않는다.

모델이 프롬프트를 어긴 경우까지 막기 위해 최종 변환기는 생성 원화를
16×16로 표본화한 뒤 모든 색을 해당 지휘관의 ROM 팔레트에 맞춘다.
캐릭터별 AI 몸체·장비·탈것 실루엣은 유지하고, 클래스별 원본 얼굴·머리
마스크 픽셀은 바이트 단위로 복원한다. 기본 클래스는 계속 ROM 원본과
완전히 같다.

예외적으로 사용자가 선택한 엘윈 로드·하이로드·소드마스터·히어로 4개는
`direct_16x16_01_elwin.png`의 보병 몸체, 갑옷, 방패, 무기, 망토
실루엣을 유지한다. 이 네 결과에도 ROM 팔레트를 적용하고, 얼굴·머리·눈
사각형은 해당 클래스 원본 픽셀로 다시 덮어 정체성을 고정한다. 따라서
기본 클래스는 `AI 클래스` 탭에서도 ROM 원본과 완전히 같고, 직접 선택한
네 상위 클래스만 합본 디자인의 실루엣을 사용한다.

`AI 클래스` 검사기의 16×16 얼굴 마스크 편집기는 현재 자동 마스크를
자주색 격자로 보여 준다. 클릭으로 한 픽셀을 전환하고 드래그로 연속
추가·제거할 수 있다. `마스크 저장`은
`editor/ai_identity_masks.json`에 해당 클래스의 픽셀 좌표만 즉시
저장한다. 저장 시 170개 미리보기 PNG나 비교 시트는 다시 만들지 않는다.
저장된 좌표는 다음 AI 이미지의 16×16 변환 때 읽어 적용한다.
`자동값 불러오기` 후 저장하면 해당 클래스의 사용자 오버라이드를 제거한다.
이 마스크와 AI 디자인은 실제 ROM 빌드에는 들어가지 않는다.

같은 검사기의 `16×16 캐릭터 디자인 편집`은 최종 적용 PNG를 16×16
격자로 확대해 보여 주고 연필·지우개·채우기·스포이드·실행 취소와 다시
실행을 제공한다. 색상 선택기의 임의 RGB는 가장 가까운 메가드라이브
채널값으로 보정하며, 투명색을 제외한 4bpp 가시색 15개 제한을 저장
API에서도 검사한다. 얼굴 마스크 좌표는 자주색 테두리로 표시하고 수동
디자인에서도 수정하지 못하도록 잠근다.

`다른 AI 그림 불러오기`는 로컬 PNG/JPG/WEBP/GIF를 브라우저 참고
창에서만 열어 현재 AI 원화 대신 확대해 볼 수 있게 한다. 참고 파일은
서버나 프로젝트에 복사하지 않는다. `이 디자인 저장`은 전체 170개를
재생성하지 않고 선택 클래스 PNG 하나와
`editor/ai_class_design_overrides.json`만 원자적으로 갱신한다. 저장한
256개 RGBA 픽셀은 다음 전체 AI 자산 빌드 마지막 단계에도 다시 적용된다.
`수동 편집 삭제`는 첫 편집 직전 자동 변환본으로 복원하고 오버라이드를
제거한다.

`tools/build_character_ai_comparison_sheets.py`는 지휘관마다 AI 원화,
최종 16×16, ROM 원본을 한 카드에 나란히 둔
`<character>-ai-and-16x16.png`를 `character-ai-v3`의 각 캐릭터 폴더에
만든다. 얼굴과 머리, 실루엣을 한 파일에서 비교할 수 있다.

`tools/pixellab_elwin_inpaint.py`의 초기 로드 실험은 아래쪽 손을 얼굴로
잘못 골라 몸통을 잠갔고, 이후 실루엣 전체를 잠근 후보는 30픽셀
재색칠에 그쳐 클래스 차이가 보이지 않았으므로 폐기했다. 해당 실험
파일은 실패 원인과 마스크 회귀 검증용으로만 남긴다.
